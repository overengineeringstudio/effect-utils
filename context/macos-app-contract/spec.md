# macOS app contract: single permissions host

This document specifies one stable permission-bearing host and its client and
release contracts. It builds on the accepted
[single-host decision](./.decisions/0001-single-permissions-host.md).
This directory has no separate vision or requirements document.

## Status

Draft. A real unsigned native permissions host is the implementation target;
implementation has not yet been verified. Existing `mkMacosApp`, `macos-app-ctl`,
sealed-release and native security primitives are reusable implementation inputs.
No signing, installation, launch or permission grant is authorized by this work;
those require an explicitly authorized human-present session. No production grant
or tool migration is established here. Positive platform release gates remain in
[open-questions.md](./open-questions.md).

## Scope

The contract defines host identity, typed operations, local IPC, policy, audit,
consent, assembly and migration. Changing CLIs, native apps, tray apps and agents
are clients; they do not acquire the host's grants themselves.

It does not define arbitrary execution, shell/script evaluation, caller-selected
plugins, an arbitrary filesystem proxy, root privilege escalation, a universal
permission-inheritance container, MDM deployment, or automatic TCC modification.
Product UI and business orchestration remain outside the protected host unless
reviewed as a specific host operation. A common installer over independently
consented product apps does not satisfy the single-host contract.

## Host process and ownership

```text
effect-utils (public)                 consumer repo
runtime + IPC + audit + Nix module -> config + private operations
          + generic operations       -> assemble unsigned single app
                                     -> seal -> install -> launchd
clients (same UID, local or SSH) ------typed IPC------> signed host
                                                   -> protected API
                                                   -> bounded result + audit
```

One consumer-assembled app holds all grants its operations need. The consumer
repo fixes a descriptive, consent-facing display name before the first grant
(for example "Mac Permissions Host"); renaming later is a re-consent migration.
The public runtime binary is `macos-permissions-host`. The public assembly module
requires `bundleId` as consumer input; it does not select or publish the final
private identity. The consumer pins its bundle identifier, canonical app basename,
install path, launchd label and actual designated requirement before the first grant.
The required ctl config string `appBundleName` is the exact filename including
`.app`, generated by Nix as `${displayName}.app`. It is one nonempty basename,
not a path. Every product bundle that is signed, sealed, staged, retained or
installed keeps that name; mutations require `--app-dir` to have that basename.
An incoming desired bundle may have an unrelated filename and cannot select the
output name. This keeps macOS System Settings permission/background-item names
readable and product-specific even when macOS observes a temporary or retained
copy rather than the installed bundle.

Nix's unsigned `hostApp` output retains its technical `${name}.app` filename for
source consumers; `hostAppBundle` exposes that complete source path without
requiring consumers to reconstruct it. Only ctl-created signed copies use
`appBundleName`; the source filename is never registered or granted authority.

launchd starts the installed signed native entrypoint directly, never a resident
shell, resource-accounting wrapper or client. A socket/SSH client does not launch
a replacement host when the service is absent. GUI-dependent operations require
the host's GUI-session execution context; absence returns `session-unavailable`,
not a fallback to another privileged app. A system-domain supervisor and a
GUI-session agent may share the single signed bundle and consent identity.

Protected APIs and policy execute in the host or its declared supervised children.
Compiled, reviewed operations are not external action commands. The host fixes
each child's executable, argv, environment, working directory and file descriptors;
clients cannot choose or override them. Supervision does not introduce an
execution API.

### P2 runtime design: two jobs, one principal

The system-domain supervisor runs directly from the signed bundle as the explicit
target user and owns the sole public client socket. The GUI-domain agent runs the
same signed entrypoint with a distinct role and owns only a private, owner-only
forwarding socket. Both ends authenticate the kernel peer UID and validate the
peer's live code against the pinned host signing requirement. Signing identity
alone does not establish a role: a same-UID caller can launch the unchanged
signed executable with a copied policy. Each peer additionally binds the kernel
peer PID/incarnation to the current launchd-managed job, using fixed
`/bin/launchctl` job evidence and immutable target UID/job labels from the
bundle-sealed `Contents/Resources/runtime-identity.json`, never caller-selected
config. This binding is refreshed before dispatch and response.
The system domain requires root management, but the target UID controls
`gui/<uid>` and can replace its agent under the correct sealed label. Job PID
evidence therefore does not grant policy authority. Every production entrypoint
loads only the verified bundle's `Contents/Resources/policy.json`; `--config`
is accepted only when its bytes exactly equal that sealed resource, otherwise
typed `policy-denied` is returned before Host construction. Serving additionally
requires non-JSON provenance from this loader. Private request and response
`policyRevision` fields carry SHA-256 of the actual verified policy bytes, not
the caller-declared revision string; both sides require the sealed digest plus
release revision. Replacing a GUI job cannot install attacker-selected child
argv/environment/paths, even while retaining the declared revision strings.
All exchanges are bounded.
The supervisor routes only compiled GUI operations;
clients cannot select a transport or another endpoint. A missing GUI agent yields
`session-unavailable`, never client autospawn or execution in a substitute app.

The system job survives GUI logout; launchd creates and removes the GUI job with
the login session. Each role owns only children matching its session requirement.
Shutdown first closes admission, then signals and reaps its children within their
declared grace periods, before releasing its endpoint. Release installation
switches the bundle, selected generation and both launchd configurations as one
recoverable transaction. Any post-exchange failure restores the prior bundle,
generation and configurations and reconverges both jobs; an absent GUI session
is distinct from a failed system supervisor.

Each child has one lifetime-owned slot: inactive, starting, running, backoff or
stopped, plus a separate ready/deferred/failed probe outcome. Admission reserves
the slot before spawning, so overlap returns `skipped: already-running`.
Only declared resident activation or a compiled scheduled operation may start it.
Spawn and readiness failures and unexpected exits spend a bounded lifetime retry
budget with capped exponential backoff; successful readiness does not reset it.
Explicit stop suppresses restart, sends the declared signal, waits the declared
grace and then kills/reaps the process group. Scheduled invocation results retain
the actual exit code/signal; nonzero exit alone never becomes deferral. Only a
compiled, permission-specific probe can produce deferred evidence, retained in
bounded private audit rather than public status.
An idle scheduled child reports the declared readiness kind with
`evidence: scheduled-idle`, both before its first invocation and after successful
completion; this is schedule admission, not evidence that a probe executed.
Readiness/exit audit failure unconditionally stops and reaps admitted work,
publishes `failed: audit-unavailable`, and suppresses restart. Internal safety
cleanup and cancellation never depend on admitting another audited client stop.

ProcessType is inherited from the owning launchd job, not independently changed
after spawn. Build-time admission requires each child's declared ProcessType to
equal its role's job ProcessType; runtime repeats that check defensively.
The child applies nofile limits and nice before exec using only async-signal-safe
`setrlimit` and `setpriority`, and a failed call fails spawning with a typed error.
The alternative private `posix_spawnattr_setprocesstype_np`/SETEXEC trampoline was
rejected: its undocumented ABI would add an unnecessary security boundary.
Consumers needing different process types must choose compatible job-level
policies explicitly; the runtime never silently changes a GUI job for a backup.

`ChildOperations` registration is compiled Rust assembly, separate from immutable
declarations. The production registry is empty by default: unknown probes,
scheduled IDs, session-incompatible registrations and mismatched scheduled child
bindings fail closed. The explicitly enabled offline example registry provides
`example.ready` and `example.run`; it does not supply a Watchman or restic adapter
or claim protected-resource access.

### Public runtime and private assembly

| Owner         | Contents                                                                                                                                                       |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| effect-utils  | Host runtime, typed IPC and clients, audit machinery, Nix module, generic operations and their schemas/policy validation                                       |
| Consumer repo | Folder/source allowlists, caller labels, local state destinations, private operations, enablement, final app assembly, pinned identity, signing and activation |

A generic operation is added by an effect-utils PR defining schemas, policy,
required grants, audit metadata, cancellation/commit behavior and tests. After it
lands, the consumer repins effect-utils, enables/configures the operation,
assembles and seals a new host release, verifies it and obtains any new category
or Automation-target consent. New clients using an existing enabled operation
require neither a host identity nor a permission grant. Private operations link
into the same assembled host and receive the same whole-disk-authority review;
private configuration, source paths and labels never enter the public repo.
No dynamically loaded client code bypasses assembly and sealing.

## Supervised children

The host is the single macOS permissions principal. Tools such as a filesystem
watcher or backup helper execute as supervised children, not separately granted
apps, external Nix-store payloads or shell wrappers. Declaration admission,
supervision, readiness and active-child verification share the immutable policy.
Inactive declarations never spawn or probe. Positive platform evidence for real
protected-resource access and pre-login behavior remains a separate release gate.

### Declaration and pinned bundle boundary

[`children.schema.json`](../../nix/macos-app/children.schema.json) defines the
`supervisedChildren` array in immutable consumer policy and ctl configuration.
`mkMacosApp.supervisedChildren` supplies ctl's view; `mkMacosPermissionsHost`
forwards the policy field unchanged. Omission is an empty inventory. The shared
Rust decoder rejects unknown fields at every declaration/tagged-object boundary,
duplicate IDs/helper paths, non-nested helpers, traversal and Nix-store executable
paths. JSON Schema additionally describes the structural contract; cross-entry
uniqueness, limit ordering, socket/run-directory agreement and
`initialBackoffMs <= maxBackoffMs` are semantic decoder checks.

| Field                 | Contract                                                                                                                                                                                                                                                                                             |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                  | Unique `[a-z][a-z0-9-]*`, at most 128 ASCII characters.                                                                                                                                                                                                                                              |
| `helperPath`          | Canonical bundle-relative `Contents/Helpers/...` executable; no empty, `.` or `..` components, backslash, NUL, absolute or store path.                                                                                                                                                               |
| `argv`, `env`, `cwd`  | Complete fixed argument list (excluding argv[0]), environment map and canonical absolute working directory. No ambient environment merging, NUL, or environment keys containing `=`. cwd and probe socket paths cannot be in `/nix/store`.                                                           |
| `requiredTccServices` | Unique grant-category strings: `full-disk-access`, `notifications`, `screen-recording`, `accessibility`, `microphone`, `system-audio`, `automation`. A declaration is not evidence of a grant.                                                                                                       |
| `requiresSession`     | Required `none` or `gui`. Session-free children belong to the supervisor; GUI children require its authenticated GUI-session execution context.                                                                                                                                                      |
| `readiness`           | `{kind:"socket-accepts",path,timeoutMs}`, `{kind:"probe-op",op,timeoutMs}` or `{kind:"none"}`. Timeout is 1..300000 ms. `op` is a compiled, enabled, nonprompting bounded host probe returning the typed result below, never a client-supplied command. Plain `exit-zero` declarations are rejected. |
| `restart`             | `{kind:"never"}` or `{kind:"on-failure",initialBackoffMs,maxBackoffMs,maxAttempts}`. Backoff is 1..300000 ms, initial <= maximum, attempts 1..100.                                                                                                                                                   |
| `stop`                | Required `{signal:"int"                                                                                                                                                                                                                                                                              | "term",graceMs}`; send SIGINT or SIGTERM, wait 1..300000 ms, then SIGKILL only if still alive. |
| `activation`          | `active` or `inactive`; omitted means **inactive**. Backup tools remain inactive/shadow declarations until separately proven and explicitly activated.                                                                                                                                               |
| `schedule`            | `{kind:"resident"}` or `{kind:"launchd-scheduled",op}`. Scheduled operation IDs name compiled work; restart must be `never` because launchd owns the next invocation.                                                                                                                                |
| `rlimitNofile`        | Required closed `{soft,hard}` positive unsigned-64-bit limits with soft <= hard; reject unsupported platform limits before spawn.                                                                                                                                                                    |
| `nice`, `processType` | Required nice -20..19 and launchd `ProcessType`: `Background`, `Standard`, `Interactive` or `Adaptive`.                                                                                                                                                                                              |
| `directories`         | Required closed `{state,run,log}`, each `{path,mode?}`; distinct canonical absolute non-root/non-store paths. Default mode 0700 (decimal 448), explicit modes 0000..0777. Owner is always the target UID, never client input.                                                                        |
| `clientSocket`        | Optional fixed canonical absolute socket inside the declared run directory; null/omitted for tools without a client socket. `socket-accepts.path` must equal it.                                                                                                                                     |

Operation names consist of two dot-separated declaration-ID segments. Assembly
must resolve probe/scheduled IDs against the compiled registry and reject absent,
disabled, prompting or execution-like implementations; syntax alone does not
register an operation. Scheduling names an existing consumer launchd-scheduled
host operation; it does not add a timer/cron DSL or let launchd execute the helper
directly.

Every declared required TCC service must also be enabled in host policy.
Assembly and runtime reject disabled categories before admitting child work;
disabled policy is not permission deferral and cannot request onboarding.

Before spawning, the host creates the declared state/run/log directories as the
target UID with their declared modes (0700 unless explicitly overridden). Reject
foreign ownership, symlink traversal, incompatible existing modes and unsafe ACLs;
do not chmod arbitrary preexisting trees or silently widen access. No client may
choose these paths.

`clientSocket` is a **release invariant**, not a per-generation scratch pathname:
the daemon's fixed argv/config, compiled probe operation and clients' fixed
sockname must agree across upgrade and rollback. ctl must compare the desired
and incumbent endpoint and reject changes without an explicit reviewed endpoint
migration; a matching path in JSON alone does not prove argv/client agreement.
Children supporting client autospawn must have it disabled by their immutable
configuration. A stopped/replacing host never authorizes client-side spawning.

Apply the declared resource policy before child work. ctl must also verify the
host job's own Nice/ProcessType and effective nofile limits, not just the child's
requested values. A child can refuse startup above a known nice threshold, and
an unprivileged host cannot lower an inherited nice value; incompatible inherited
policy is a hard admission failure, never a failed launch followed by a silent
fallback. ProcessType is the owning launchd job's inherited property, not a claim
that setting nice alone changes background scheduling. Child declarations must
match that job's ProcessType at assembly; no private process-policy API is used.

Every helper is a pinned, signed nested code object in the complete host bundle,
covered by the explicit `nestedCode` inventory and unsigned descriptor/sealed
receipt. Copy real bytes during assembly; a symlink to a store executable is not
a nested helper. Verify its pinned designated requirement and sealed content before
spawn. Runtime resolution must stay inside the installed bundle after symlink
resolution; a lexically valid declaration alone is not executable admission.
The permissions-host assembly's `helpers` inventory copies and inventories real
nested helper bytes and pins the requirements used for runtime admission.

### Spawn, scheduling and ownership

Spawn directly **without a responsibility disclaim**; do not use
`responsibility_spawnattrs_setdisclaim`, detach to another permissions principal,
or invoke a separately launched service. TCC is expected to evaluate the host,
as observed for the bounded non-disclaimed-child experiment; every real helper
and launch topology still requires positive protected-resource evidence. There
is no `core.exec` or other client-chosen execution operation.

The supervisor supplies the pinned executable, exact argv/env/cwd, stdin from
`/dev/null`, bounded captured stdout/stderr, and no other inherited descriptors.
Children cannot inherit request sockets, audit descriptors, signing material or
lifecycle locks. Stop/reap children before host shutdown or replacement, applying
the declared stop signal and grace period on upgrades/restarts as well. A
resident starts only when active; a scheduled child starts only inside its
declared host operation and is reaped before that invocation completes.
Every child ID is single-instance: a scheduled or requested start while that ID
is running returns `skipped: already-running`, records it in audit/status and
never launches a parallel instance. No catch-up queue accumulates overlapping work.

The runtime adds typed operation `children.stop`, version 1, with closed
input `{id: string}` (a declared child ID, never a PID or executable), stopping
exactly that child using its declared protocol. The result names the child and
instance, whether it was already stopped, and its actual exit code/signal.
Normal peer/policy/audit admission applies; the caller cannot choose a signal,
extend grace or stop an undeclared process. An explicit stop suppresses resident
restart until a subsequent authorized activation/start, rather than racing
the supervisor's restart loop.

The host owns resident restart accounting and capped exponential backoff:
`min(maxBackoffMs, initialBackoffMs * 2^attempt)`. The first retry is attempt zero;
`maxAttempts` caps retries after the initial spawn within one host lifetime.
Unexpected exit, spawn failure and readiness timeout consume this budget;
intentional shutdown, inactive configuration and pending consent do not.
Exhaustion is failed, not an endless restart loop. A successful readiness probe
does not reset the lifetime budget.

Pre-login-capable children must work under a system LaunchDaemon running the
consumer's explicit non-root UID before graphical login. `gui/<uid>` success is
not proof of this topology, and the absence of a GUI must never silently select
a second app identity. GUI-only probes report session failure, not readiness.

Declarations are independent of the launchd job executing them. Each compiled
operation also declares `requiresSession: "none" | "gui"`; a probe/scheduled op
must be compatible with its child's session requirement. The contract requires
one signed bundle with two direct-entrypoint jobs: `requiresSession: none`
children/ops run in the system-domain supervisor LaunchDaemon with `UserName`
set to the target user and work before graphical login; it owns the single
client endpoint. Only `gui` children/ops run in the `gui/<uid>` agent, reached
through a private mutually authenticated socket (notifications, capture,
Accessibility and Automation). GUI requests return `session-unavailable` while
that session is absent. ctl treats the paired configurations as one release
transaction; positive pre-login proof remains a platform acceptance gate.

Both jobs run as the same explicit target UID. For the system supervisor,
`UserName` resolves to that target user, not root; ctl validates it against
`--target-uid` and requires matching `UserName` for a non-root system target
([`launchd.rs`](../../nix/macos-app/host/src/bin/macos-app-ctl/launchd.rs),
`account_names` and `validate_value`). The GUI job is loaded in `gui/<uid>` for
that same UID; ctl rejects a domain UID differing from `--target-uid` and rejects
`UserName`/`GroupName` overrides outside the system domain. Children inherit their
host job's UID without setuid/setgid or other privilege changes. There is
deliberately no per-child user field; unknown-field rejection prevents declaring
a child-specific execution identity.

### Readiness, status and audit

Activation/lifecycle (`inactive | starting | running | backoff | stopped`) is
distinct from the readiness outcome below. Starting/backoff are not ready.

A compiled `probe-op` returns exactly the schema's `probeResult`:
`{outcome:"ready"}`, `{outcome:"deferred",service,evidence}` or
`{outcome:"failed",code}`. Deferred evidence is nonempty, bounded to 4096 characters,
permission-specific and tied to the current child/release; generic socket failure
or nonzero exit is not permission evidence. It stays in private audit; public
status carries only the stable service/reason. The compiled operation validates
the evidence semantics, not the client or arbitrary stderr.

For a filesystem-watcher child, a real watch-list request over its fixed socket
proves application readiness; `socket-accepts` proves connection readiness only.
Full Disk Access evidence requires **both plain and rename-exchange FSEvents
probes** as a compiled child-specific host operation. Connection success, a
watch-list success or one FSEvents shape alone cannot establish FDA capability.

| Outcome    | Evidence and transition                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ready`    | Declared socket accepts a connection within its deadline (connection-only evidence), or the compiled probe returns typed `ready` (application/permission evidence defined by that op). File existence and PID presence are insufficient. `none` explicitly opts out of a service-readiness claim: after successful spawn, report `ready` with `probe:"none"` and `evidence:"spawn-only"`, never socket/application readiness. A scheduled idle child reports `ready` only with authenticated scheduling evidence, `evidence:"scheduled-idle"`; that does not claim a completed backup. |
| `deferred` | A compiled probe returns typed deferred with permission-specific evidence for a declared required service. When classifying a child/process exit, only actual exit **75 together with** `deferred-admission: pending-grant: <service>` stderr and permission-specific probe evidence permits deferred. A bare 75, diagnostic without 75, timeout or unknown service is failed. Stop admissions/retries until explicit re-evaluation.                                                                                                                                                   |
| `failed`   | Invalid bundle/signature/policy, probe error or deadline, unexpected termination, missing session, or exhausted restart budget. Preserve a stable error code and last observed outcome.                                                                                                                                                                                                                                                                                                                                                                                                |

A ready child returns to starting on restart and loses old readiness evidence.
An explicit re-evaluation may move deferred/failed to starting; ready requires a
fresh probe for the current release and instance. Denied or unknown authorization
never becomes ready from a PID. Inactive is outside this state machine and cannot
be reported as ready or deferred.

`host.status` adds a sorted `children` inventory with the following redacted
projection (never argv, environment, executable/private paths or log contents):

```typescript
type ChildStatus = {
  id: string
  activation: 'active' | 'inactive'
  schedule: 'resident' | 'launchd-scheduled'
  requiresSession: 'none' | 'gui'
  state: 'inactive' | 'starting' | 'running' | 'backoff' | 'stopped'
  readiness:
    | null
    | (
        | {
            outcome: 'ready'
            probe: 'socket-accepts' | 'probe-op' | 'none'
            evidence: 'probe-passed' | 'spawn-only' | 'scheduled-idle'
          }
        | { outcome: 'deferred'; service: string; reason: string }
        | { outcome: 'failed'; code: string }
      )
  instanceId: string | null
  pid: number | null
  restartCount: number
  nextRetryAt: string | null
  lastExit: null | { code: number | null; signal: number | null }
  lastStart: null | { outcome: 'started' | 'skipped'; reason: null | 'already-running' }
  policyRevision: string
  releaseRevision: string
}
```

Append bounded audit events for admission, spawn, probe outcome, deferred grant,
exit, retry scheduling/exhaustion and stop. Events contain `auditId`, UTC timestamp,
`childId`, `instanceId`, event kind, prior/new state, readiness outcome/reason code,
restart count, release/policy revisions and exit code/signal where applicable.
Audit loss denies new child admission. Bounded child stdout/stderr logs are
separate from audit, use existing private log retention, and never enter status or
the activation verifier's public diagnostic envelope.

Record the child's real exit status unchanged in `lastExit` and audit (including
75); a signal termination has a null code and actual signal, not a fabricated
shell-style exit code. Classification never replaces the child's exit code with
ctl's aggregate status. Only the paired exit-75/deferred-admission evidence above
permits deferred classification of process exits; typed host probes separately
require the permission-specific evidence contract.

Runtime follow-ups also include per-child append-only stdout/stderr destinations
(never truncate during a run; retention/rotation only between runs), multiple
`StartCalendarInterval` entries for consumer launchd-scheduled host operations,
and secrets access through the op-proxy service bundle in preference to per-helper
Keychain ACLs, so signing changes do not introduce new prompts. Secret values
never enter declarations, argv, public diagnostics or audit/status. These are
supervisor-runtime requirements, not capabilities implemented by this PR.

### ctl verify and activation admission

The supervisor runtime's ctl verifier must authenticate the running host and its
release/policy before consuming `children`. Compare the exact desired inventory,
activation and schedule, then report each child's outcome; do not infer child
health from the host PID. All active children ready (or inactive by declaration)
means exit 0. Any failed/missing/stale child evidence means a hard verification
failure (exit 22), taking precedence over deferred children. If no hard failures
exist and any active child is deferred, return exit **75** with diagnostic
`deferred-admission: pending-grant: <service>` and structured child IDs/service
reasons. Activation must retain this as deferred admission, not stamp complete,
roll back a valid install merely for pending consent, or treat exit 75 as ready.
Verification never prompts.

ctl validates immutable child declarations before mutation and authenticates live
child evidence through the existing controller status protocol. Inactive children
have null readiness and cannot satisfy active readiness. A successful offline
example establishes protocol and lifecycle evidence, not TCC or pre-login proof.

Paired ctl configuration supplies `session = "system-daemon"`, an explicit
non-root `targetUid`, and `launchd` plus `guiLaunchd` declarations.
`converge-launchd` uses `--plist-dir` and `--gui-plist-dir` for the two
configuration directories and `--gui-socket` for the private endpoint. The
private socket needs its own owner-only directory, separate from both public
protocol sockets. `--domain` defaults to `system`; `--target-uid` defaults to
the immutable configured target. Supplied `--plist` and `--gui-plist` must occur
together and name the same installed entrypoint with exact `serve --role
supervisor|gui-agent --gui-socket ...` arguments.

The existing `D.rollback.json` exchange journal owns bundle, generation and paired
configuration/job recovery; there is no parallel paired release journal.
Recovery validates the recorded stage, archive, identity and all required inputs
before stopping any live job. Missing or unverifiable prerequisites retain the
journal and return a typed unresolved error without booting out services.
Recovery after an error or crash restores the complete incumbent release before
restarting its jobs. GUI restoration follows current GUI-domain availability,
not just whether the agent was loaded before the transaction: login during a
failed release must restore the old agent, and logout must not fabricate GUI
success. Unresolved recovery retains the journal for the next ctl invocation.
A pair receipt pins the installed
bundle inode and both configurations. With no GUI session, ctl publishes the GUI
configuration but starts only the system job; this is not a substitute GUI
success. Child verification gives hard failures precedence (exit 22); only
explicit typed permission deferral uses exit 75 and `error.details.children`.
Lifecycle contention uses exit 23 rather than impersonating permission deferral.

## Typed operation registry

```text
compiled operation ID + version
  -> request/response/error schemas
  -> permission/session requirements
  -> immutable consumer policy
  -> reviewed native implementation
  -> audit projection + lifecycle/commit rules
```

The registry is compiled into the assembled host; startup rejects duplicate
ID/version pairs, invalid policy and enabled operations without implementations.
A manifest cannot add behavior the host does not implement. One schema source
derives host decoding and client types; unknown fields are rejected rather than
passed to a command. Status advertises enabled ID/version pairs and policy
revision, not executable paths or private source configuration.

Operation IDs are case-sensitive repository-local protocol names stewarded by
effect-utils. The runtime registers `host.status`, `documents.copy`, `notify` and
`children.stop`, plus explicitly compiled product scheduled operations.
Dotted names use `[a-z][a-z0-9-]*\.[a-z][a-z0-9-]*`;
`host.*` and `documents.*` are public namespaces and `private.*` is allocated
only by the assembling repo, with no interoperability across consumers.
`notify` is the sole explicitly registered single-word exception: retain the
assigned public wire ID rather than invent a `core.notify` rename or alias.
This replaces the draft's `core.*` examples/reservation; `core.notify` and
`core.copy-allowlisted` are not registered operations. Other bare names,
`Core.Notify` and any arbitrary-execution operation are invalid. There is no
registered Internet namespace. `operation` selects semantics;
`operationVersion` selects its positive-integer schema version. Breaking changes
get a new version, never reinterpret an old request. Host upgrades may retain
supported versions explicitly; unsupported versions return `unsupported-version`
without work. Protocol framing has its own `protocolVersion`; it is not an alias
for the operation version.

### Request and response envelopes

```typescript
type Request = {
  protocolVersion: 1
  requestId: string // caller correlation only; 1..64 ASCII [A-Za-z0-9_-]
  operation: string
  operationVersion: number
  callerLabel: string // asserted, unauthenticated; 0..128 UTF-8 bytes
  input: StatusInput | CopyInput | NotifyInput // selected by operation + operationVersion
}
type Response =
  | {
      protocolVersion: 1
      requestId: string
      ok: true
      result: StatusResult | CopyResult | NotifyResult
    }
  | {
      protocolVersion: 1
      requestId: string | null
      ok: false
      error: {
        code: ErrorCode
        message: string
        auditId: string | null
        actionRequired?: { category: string; nextStep: string }
      }
    }
type ErrorCode =
  | 'invalid-request'
  | 'unsupported-version'
  | 'unknown-operation'
  | 'caller-denied'
  | 'policy-denied'
  | 'permission-required'
  | 'session-unavailable'
  | 'busy'
  | 'deadline-exceeded'
  | 'audit-unavailable'
  | 'operation-failed'
```

`permission-required` includes `actionRequired.category` (one of the seven grant
strings below) and a bounded `actionRequired.nextStep` describing the
human action. For Automation the step identifies the affected allowlisted
target. This is a typed denial, not permission to launch onboarding from a
request. Other errors do not imply consent is missing.

Every operation supplies concrete input/result schemas and bounded public error
messages. The envelope above is the target operation protocol, not the existing
[`wire.schema.json`](../../nix/macos-app/wire.schema.json) ctl/status wire. Keep
control status distinct; migrate callers rather than silently reinterpreting old
action requests. Request IDs are not authentication or a generic exactly-once
guarantee. A disconnect can leave an outcome unknown; clients must not blindly
retry mutations. Each operation defines replay, commit and result-query behavior.

The `macos-app-ctl` process failure envelope is
`{ "ok": false, "error": { "kind": string, "category": string | null, "reason": string, "exitCode": integer } }`.
`error.exitCode` equals the process exit status; consumers use it rather than
maintaining a kind-to-exit-code table. This is distinct from the operation
response envelope above. Intentional crash failpoints do not print an envelope.

## IPC and same-user trust

```text
accept -> kernel peer -> same-user admission -> bounded decode
       -> registry/version -> operation policy -> audit admission
       -> execute -> audit outcome -> response -> close
```

Use a local Unix-domain socket under a protected directory owned by the selected
user, mode 0700, socket mode 0600. Reuse `endpoint::bind` no-follow ancestry,
ACL, stale-socket and same-inode cleanup checks. A non-socket or live listener
blocks startup. No network listener or unauthenticated request-file fallback is
part of this contract. An SSH client connects locally as the same user.
`endpoint::bind` locks the entire socket parent directory. The standard ctl
socket and typed `config.socket` therefore require different precreated,
user-owned mode-0700 parent directories; different filenames in one directory
are insufficient and would contend for the same listener lock.

Ctl waits up to 15 seconds for a running launchd job's control socket, retrying
only `ENOENT` and `ECONNREFUSED` at 50 ms intervals. Each attempt rechecks that
the job remains loaded with the originally observed PID; exit or replacement
returns `job-not-running` immediately. Deadline expiry returns `endpoint-unready`
with the socket path and elapsed duration (exit 23). Other connection failures
are not retried. This wait covers supplied-plist evidence and generic host IPC;
it does not retry requests or change peer authentication or PID checks.

One newline-delimited UTF-8 JSON request and response per connection; maximum
request 64 KiB including newline, maximum response 1 MiB. Reject invalid UTF-8,
multiple/trailing requests and oversized frames. Use an absolute five-second
frame-read deadline and at most 32 admitted connections; overflow closes without
queuing unbounded work. Per-operation concurrency and execution deadlines are
separate server-side limits. No ancillary descriptors are accepted by the initial
operation protocol.

Capture the kernel `LOCAL_PEERTOKEN` audit token at accept, including PID,
incarnation and real/effective UIDs; require both UIDs to equal the configured
host user. Record the peer executable path as a kernel-observed diagnostic,
with an explicit unavailable reason if lookup fails; never substitute a
request-supplied PID/path/token. Audit token acquisition failure refuses admission.
A path lookup is not an immutable signature identity. A connected peer can
exec, exit or delegate its socket; the log describes the captured connection
peer, not an authenticated human or per-message sender.

Any same-UID process may call an enabled operation. `callerLabel` is asserted,
not authenticated and never an authorization credential. Socket permissions are
reachability, not per-tool isolation. The safety boundary is narrow operation
policy, not a bearer token readable by the same user or an interpreter allowlist.
Optional per-operation caller predicates may later use the captured token and
shared compiled-requirement checks without changing client request schemas.
Such restrictions must retain freshness/liveness limits honestly; they do not
turn asserted labels into authenticated seats.

## Per-operation policy and audit

| Policy field                        | Meaning                                                                                                   |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `enabled`                           | Explicit consumer enablement; absent means unavailable                                                    |
| `sources` / `targets`               | Consumer-selected symbolic IDs mapped to fixed roots or app targets, never caller-selected absolute paths |
| `maxItems`, `maxBytes`              | Positive finite result/work limits checked during work, not just before it                                |
| `timeoutMs`, `concurrency`          | Positive finite server-owned deadline and active-work cap; excess returns `busy`                          |
| `requiredGrants`, `requiredSession` | Operation-specific prerequisites with honest denied/unknown states                                        |
| `callerPolicy`                      | Same-user default; optional tighter predicate, never asserted-label authentication                        |
| `commit`, `cancel`, `replay`        | Operation-specific publication point, disconnect behavior and retry rules                                 |

All operations are reviewed as running with **whole-disk read authority** because
the host holds Full Disk Access. The source allowlist is application policy, not
a macOS sandbox. Reject traversal, symlink/root escapes and caller-controlled
paths; check opened file identities rather than trusting string-prefix checks.
Do not expose environment overrides, arbitrary exec or arbitrary script bodies.
Time/size bounds must be enforced throughout work. Disconnect/deadline stops
uncommitted work; a documented atomic commit may finish while retaining lifecycle
exclusion. Never release exclusion while protected work still runs.

The host owns an append-only JSONL audit under private consumer-owned state,
files mode 0600. Assign a host-generated `auditId`; record UTC time, host release
and policy revisions, operation/version, request correlation, captured peer audit
token/PID/incarnation/UIDs/executable-path observation, asserted caller label
marked unauthenticated, policy decision, symbolic source/target IDs, bounded
counts/digests, duration and terminal result/error. Record denials too; malformed
or incomplete connections use null correlation. Never log file contents,
notification bodies, secrets or arbitrary raw request text. Consumer retention
and size limits are explicit; audit storage exhaustion refuses new work with
`audit-unavailable`, not unaudited execution. Persist admission before protected
work and outcome before reporting success. A crash may leave admitted work with
unknown outcome; recovery records that uncertainty, never fabricated success.
Same-UID audit storage is operational evidence, not tamper-proof forensics.
Before admitting protected work, reserve capacity for its bounded terminal audit
record under `auditMaxBytes`. Other outstanding admissions cannot consume that
reservation; refuse new work rather than discover after a side effect that its
outcome cannot be recorded.

## Initial operations

Release one's operation IDs are `host.status` (nonprompting operation/revision
status and consent-pending observation), `documents.copy` and `notify`. Grant-category
onboarding is a separate human-present command, not an operation that socket
clients can invoke.

### Host status

Operation ID: `host.status`, operation version 1.

```typescript
type StatusInput = {}
type StatusResult = {
  auditId: string
  operations: { operation: string; operationVersion: 1 }[]
  policyRevision: string
  releaseRevision: string
  consentPending: boolean
  children: ChildStatus[]
}
```

The operation inventory contains enabled runtime IDs and compiled scheduled IDs. Status does not
expose private paths, request consent or claim that observed authorization
establishes positive access. A nonpending observation is not evidence that
DQ1–DQ9 passed. The legacy ctl status remains a distinct protocol.

### Allowlisted Documents copy

Operation ID: `documents.copy`, operation version 1.

```typescript
type CopyInput = { sourceId: string; files: string[] }
type CopyResult = {
  auditId: string
  stagingId: string
  files: { name: string; bytes: number; sha256: string }[]
}
```

This is the first protected operation. Each configured source requires `root`,
`sentinel` and explicit `allowedBasenames`; a root alone does not allow all files
within it. Callers supply only distinct allowlisted basenames (1..255 UTF-8 bytes,
no slash, NUL, `.` or `..`), never arbitrary paths. Limit
file count, total bytes and duration by consumer policy. Descriptor-relative
no-follow opens require regular files under the selected root; source changes,
symlinks, nonregular files and bound overruns refuse publication. Copy in the
host itself into a private per-request staging directory, compute hashes and
publish only a complete staged result atomically. Cleanup incomplete staging;
never return a partial success. Staging IDs are opaque host-generated names,
not caller paths. Do not overwrite an existing staged result on replay.

The existing narrow copy helper is source material for the later port, not a new
separately consented app to deploy. Preserve its allowlist, peer capture, bounded
copy, sentinel observations, hash receipts and audit semantics. A successful
sentinel/probe is evidence about that read, not a global TCC authorization oracle.
The consumer owns staging-to-inbox handoff and cleanup after import. Acceptance
requires a representative Documents copy with correlated audit/hashes **and one
successful backup import**; staging alone does not establish end-to-end readiness.

### Notifications

Operation ID: `notify`, operation version 1.

```typescript
type NotifyInput = { productId: string; title: string; body: string }
type NotifyResult = { auditId: string; notificationId: string; submitted: true }
```

`productId` selects a consumer-configured display label, not a bundle identity.
Bound the caller's title to 256 and body to 4096 UTF-8 bytes before adding the
product prefix. Work is serialized at concurrency 1. Consumer policy
`notificationMinIntervalMs` sets the minimum notification interval; rate-limit
denials return `busy`. The host posts via its own notification APIs after consent;
the banner uses the host's name/icon and prefixes the title with the product
label. No arbitrary click command, URL, script or executable is accepted.
`submitted` means the OS accepted submission, not that a banner was displayed or
read. Audit metadata excludes title/body. New tools use this operation rather
than creating notification identities. An already separately allowed notifier
may retain its identity temporarily; further unification while preserving each
app's UI and behavior is a later migration, not a prerequisite for the host.

## Grants and human consent

Release one covers all six permission families below, with two distinct audio
categories and seven concrete `enabledGrants` strings, not FDA-only delivery
with other categories silently deferred. Consumer enablement selects the needed
grants and Automation targets; compiled support does not itself grant a category.

| Grant / config category               | Scope and harmless positive onboarding check                                                                          |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Full Disk Access / `full-disk-access` | Human System Settings approval; bounded read of a configured protected sentinel                                       |
| Notifications / `notifications`       | Explicit host allowance; bounded test notification, distinguish submission from visible delivery                      |
| Screen Recording / `screen-recording` | Explicit approval; capture and verify the host's synthetic red 32×32 fixture window, never an arbitrary desktop (DQ2) |
| Accessibility / `accessibility`       | Explicit approval; bounded harmless AX interaction/observation of a test fixture (DQ3)                                |
| Microphone / `microphone`             | Explicit approval; bounded disposable test capture, never retained production audio (DQ4)                             |
| System audio / `system-audio`         | Separate AudioCapture approval; bounded process-tap capture of synthetic audio on macOS 14.4+ (DQ4)                   |
| Automation / `automation`             | Separate approval per allowlisted target; harmless typed event per target (DQ6)                                       |

One host means one stable identity, **not one universal consent click**. Each
permission type still needs approval; Automation needs approval per target.
There is no unmanaged pre-grant mechanism. The host holds FDA and every other
grant its enabled operations need, with usage descriptions/entitlements assembled
before sealing. Do not request unrelated grants merely because the host can.
Microphone success does not establish authorization for other audio categories.
System audio uses TCC AudioCapture and `NSAudioCaptureUsageDescription`;
microphone capture uses aggregate input. Neither grant substitutes for the other,
and unsupported system-audio platforms do not silently fall back to microphone.
For the system-audio positive check, the human must play harmless non-silent test
audio during the three-second capture window. Silence or a failed capture leaves
the result failed/unknown, never a fabricated authorization pass.

`macos-permissions-host serve --config PATH` never requests consent at startup.
Only `macos-permissions-host onboard --human-present --config PATH`, during an
explicitly authorized human-present session, may perform category-specific setup
and the harmless positive check for each enabled category and Automation target.
An empty Automation target allowlist grants no existing target implicitly;
onboarding skips Automation target checks until targets are explicitly supplied.
Install and verify the pinned sealed host first; explain the operations and
authority, then record actual positive outcomes, denials and remaining unknowns.
Enabling a category, inspecting authorization or observing a successful sentinel
does not itself prove all operations in that category work.

Neither startup nor an ordinary IPC request may trigger a consent prompt or
setup loop. Denial, revocation, absent approval and a new Automation target return
typed action-required denials identifying the required human step; missing GUI
returns `session-unavailable`, never a substitute identity. Never reset TCC, edit
its database, impersonate another identity or fall back to another app's grant.
Ordinary client updates need no re-consent. Host upgrade policy remains pending
DQ1: preserve pinned identity and the actual designated requirement, but do not
claim grant continuity until positive human-present upgrade/rollback evidence
establishes it for the tested categories.

## Stable signed releases and existing machinery

```text
consumer unsigned complete bundle + independently pinned policy
  -> describe-host -> desired descriptor
  -> seal-host -> immutable signed release
  -> install-host (keyless verification) -> direct launchd entrypoint
```

Reuse `effectUtils.lib.mkMacosApp` in
[`nix/macos-app/default.nix`](../../nix/macos-app/default.nix) and its complete
`hostBundle` input for the assembled native host. Existing outputs are `hostApp`,
`generation`, `requirement`, `hostSourceHash`, `desiredDescriptor`, `ctl`,
`ctlConfig` and `primitives`. `host` and `hostBundle` are mutually exclusive.
The current convenience host's generation maps actions to hashed external
payloads with enum/string/integer arguments and UID allowlists; it is **not** the
native typed registry above and must not become the host's privileged execution
interface. Its existing ctl/status protocol remains implementation evidence only.
Adding a generic operation requires a new assembled host release; policy changes
require reviewed immutable consumer configuration, never caller-supplied policy.

Pin the actual designated requirement, not its printed text. For a new identity
the builder defaults to identifier + Apple generic anchor + leaf Team ID;
incumbents retain their explicit predicates. CN, OU and leaf-certificate predicates
are not interchangeable. Security.framework compiles and checks predicates
against actual code. Matching bundle IDs or canonical requirement text does not
prove grant continuity, logical predicate equivalence or certificate-rotation
safety. Preserve a stable path and launch topology too.

Complete bundle policy declares outer entitlements/options and each nested code
object's relative path, identifier, requirement, entitlements and options. Reject
escaping/duplicate inventories, undeclared code and writable layouts; sign
nested code deepest-first, then the outer bundle, never infer with `--deep`.
`describe-host` is deterministic and unsigned. The `macos-app-unsigned` v1
descriptor binds ordered policy and a normalized full file inventory into
`hostRevision`. Normalization removes signature envelopes/resources, not ordinary
sealed resources. `hostSourceHash` alone does not cover a complete bundle.

`seal-host --desired APP --output RELEASE --keychain K
--keychain-password-fd N` is sign-only: dedicated non-login keychain, no password
in argv/environment/store, no prompts or ad-hoc fallback. Retain the existing
non-extractable-key, exact ACL/partition, trust-chain, bounded codesign and checked
relock rules in `macos-app-ctl`. Sealing checks staged content before signing and
publishes exactly `<RELEASE>/<appBundleName>`, `<RELEASE>/descriptor.json` and
`<RELEASE>/receipt.json`. Unique stage and archive names belong to parent
directories, each containing `<appBundleName>`, never to the bundle filename.
There are no generic `host.app`, `retained-*.app` or `*.app.stage-*` product copies.
Transaction stage fields and archive pointers name the canonical bundle directly,
not its unique parent; cleanup removes the parent as well as its bundle.
An existing matching valid release is reused; mismatching output is refused. The
`macos-app-release` v1 receipt inventories sealed bytes, with `sealedRevision`
separate from source/unsigned revisions. A receipt is integrity evidence, not an
authority to choose the desired identity.

An existing release with the old `host.app` layout returns typed
`reseal-required` without deleting or installing it. Regenerate it by resealing
the unsigned source; no legacy sealed-layout reader is provided. Selecting that
release, or an old-basename retained host, for rollback returns typed
`rollback-unavailable`. Rollbacks across the naming cutover require a resealed
release with the pinned product basename.
An already committed host-rollback exchange is recovered even when its journal
names an old-basename archive: the restored inode is already installed, so the
controller selects the recorded generation, converges and verifies the host,
then removes the rollback journal and rolled-away archive. The basename
restriction applies before exchanging an incompatible archived host, not after.

`install-host --desired DESCRIPTOR --artifact RELEASE --app-dir D --state S
--archive-dir R --generation G` verifies consumer-pinned desired policy, receipt,
content and actual signatures without signing credentials or fallback. Paired
products require the generation and both launchd configuration directories and
use the same release transaction for installation and `rollback`.
Keep immutable verified incumbents for rollback; invalid input leaves them unchanged.

The paired topology is fresh-install only at its initial boundary; subsequent
paired upgrades and rollbacks preserve the recorded principal. A recorded
single-job or unrecorded incumbent, or a change to bundle ID, job labels, session
or target UID, returns typed `migration-required` (exit 64) before bundle exchange,
including an otherwise matching no-op. Existing single-job products retain their
installation, upgrade and rollback behavior; this is not an implicit migration
of unrelated products into the Permissions Host.

Changing an existing child's fixed `clientSocket`, or a paired public/private
host endpoint, returns typed `endpoint-migration-required` (exit 64) before
exchange. Endpoint and topology migration require a separate explicit consumer
plan; there is no fallback reader, automatic adoption or guessed old domain.

For paired products, `install-host` requires `--artifact` and `--generation`;
`rollback --artifact --generation` uses the same transaction. Standalone
`select-generation`, local-sign install and legacy rollback are rejected for
paired products. The installation result's `admissionRequired: true` distinguishes
release convergence from child permission/readiness admission in `verify`.

Existing explicitly selected `--incumbent legacy` only relaxes unrecorded
incumbent layout compatibility, never strict outer signature, bundle ID or pinned
identity checks. Recorded incumbent configurations govern their own validation;
an invalid record cannot be bypassed with the legacy flag. This facility is not
a grant-transfer mechanism between product and host identities.

Consumer activation owns serialization, generation GC roots, readiness verification
and explicit recovery policy. Paired ctl installation owns the coherent bundle,
generation and two-job switch, rather than separate consumer-selected commit points.
Preserve `--lifecycle-fd` exclusion and the consumer's pre-check interval; shared operation
admission retains exclusion until work finishes. ctl's acquiring `flock` check
is not proof the preceding interval was locked. Sign-only sealing is separate.
Use the existing journaled atomic-exchange installation/rollback behavior rather
than implementing a second installer. A no-op does not restart the host.
Supplied launchd plists must name the direct installed native entrypoint and
explicit domain/UID; scheduled idle evidence is distinct from a running process.
Status separates desired/installed/running release, policy and session state;
a launchctl PID alone is not authenticated running-code evidence.

Implementation sources: [`macos-app-ctl.rs`](../../nix/macos-app/host/src/bin/macos-app-ctl.rs),
[`wire.schema.json`](../../nix/macos-app/wire.schema.json), and the shared native
security modules in [`host/src`](../../nix/macos-app/host/src). None of these
mechanisms establishes historical TCC continuity without positive platform tests.

The public unsigned assembly module is
[`nix/permissions-host/default.nix`](../../nix/permissions-host/default.nix).
Consumers normally call `effectUtils.lib.mkMacosPermissionsHost` with `pkgs`,
`bundleId`, `displayName`, `signer` (`teamId`, `identity`) and ordered `policyFiles`.
Direct imports take `pkgs` and `nixpkgsRevision` before those assembly inputs. Optional
inputs are `name`, `launchd`, `guiLaunchd`, `helpers`, `enabledGrants` (all seven
concrete grant strings by default) and `automationTargets` (empty by default).
`helpers` maps fixed IDs to pinned native executable derivations and optional
identifier/requirement/signing metadata; assembly copies regular executable bytes
to `Contents/Helpers/<id>` and includes them in `nestedCode`. The consumer supplies
the identity; public examples must not expose the final private value. Signer
metadata pins the intended requirement but unsigned assembly does not sign it.

Policy files are JSON objects applied in order with shallow top-level overrides:
later lists and objects replace earlier values, not deep merge.
`enabledGrants` and `automationTargets` module arguments are authoritative;
the files supply the remaining runtime configuration.
`notificationMinIntervalMs` defaults to 1000 milliseconds and must be in the
finite inclusive range 1..3600000; it is consumer configuration, not request input.
`hostRequirement`, `helperRequirements` and the `jobProcessTypes` role map are
assembly-owned policy values, not file overrides. `enableExampleChildren` is an
explicit build-only switch for the offline example's compiled operation registry;
it defaults off and is included in source identity.
Outputs include the standard `mkMacosApp` `hostApp`, `requirement`, `ctl`,
`ctlConfig`, `generation`, `desiredDescriptor` and `primitives`, plus `runtime`,
merged `policy`, `infoPlist`, `entitlements` and `hostSourceHash`. Outputs are
lazy: `hostApp` is the unsigned permissions app. Building generic tooling such
as `ctl`, `primitives` or `desiredDescriptor` may run its existing ad-hoc-signing
build steps; that does not seal or authorize activation of the permissions app.
The app remains unsigned until explicit sealing in the authorized session.
`Info.plist` includes `MacPermissionsHostPolicyHash`, a digest of the exact merged
policy JSON and entitlement plist bytes. This binds policy-only and entitlement-only
changes to the metadata identity already compared by `macos-app-ctl`; the compiled
`hostSourceHash` need not change. `identity-tests.nix` asserts both upgrade cases
without assembling or signing a bundle. `infoPlistData` and `bundlePolicyHash`
expose the corresponding immutable metadata for consumer evaluation.

The native runtime implements the standard ctl socket lifecycle separately
from the policy-configured typed-operation socket. These are distinct protocols:
ctl lifecycle commands do not reinterpret operation requests, and ordinary
operation clients cannot trigger lifecycle changes or consent.

Persisted consent state is read using an initial nonblocking open and checked
for the expected regular-file type before decoding. A FIFO must be rejected,
not allowed to hang startup before file-type validation.

### Implementation and verification boundary

The public Rust runtime lives in `nix/permissions-host/host`; its binary accepts
`serve --config PATH` and the explicitly gated `onboard --human-present --config
PATH`. Unsigned assembly is real implementation work, not permission to sign,
install, launch or grant the app. Such activation awaits the human-present
session; building an unsigned artifact is not positive permission evidence.

Builds and tests run only while a dedicated secondary build host is idle, at
`nice` level 19, with Nix `max-jobs = 2` and `builders = ""`. Do not drain CI,
commandeer active capacity or silently fall back to another host. No build/test
pass or runtime success is claimed by this specification.

## Migration contract

```text
pause new product identities -> rewrite contract -> human-present experiments
  -> single host + Documents copy + successful import
  -> migrate each other operation -> retire superseded helper identities
```

Until the host provides the replacement operation, only grant-neutral changes
(add no consent identity and require no new approval) land. Per-product identity
rollouts remain paused; existing working helpers need not stop. This is a
transition rule, not permanent approval of independent permission identities.

For each tool, inventory its protected operation, required session/grants and
lifetime; move only the protected work into a reviewed host operation; migrate
all clients to typed IPC; obtain positive operation evidence and product-level
acceptance; disable the obsolete service and retire its separate consent
identity. Preserve product UI/business behavior outside the host. Never claim
that a helper's old grant automatically transfers to the host. Restic and
Watchman move under the host later and their identities retire; pinned-worker
and root-daemon feasibility are explicit gates, not reasons to expose exec or
silently keep permanent exception identities. The temporary already-allowed
notifier exception is described above.

## Evidence limits and open design questions

Experiment [0001](./.experiments/0001-tcc-attribution/README.md) T7/T9 establishes
that the launchd-started host is evaluated for socket/SSH-origin FDA-denied
reads. T5 establishes the same evaluated subject for a non-disclaimed child in
that denial fixture, **not positive access or universal grant inheritance**.
The other experiments are bounded fixtures: panel content, sealed-bundle
boundaries, audit-token checks and lifecycle/descriptor behavior. Their recorded
passes, blocked runs and skipped launchd cases retain their original scope.

- **DQ1 Host upgrade continuity:** Which release/DR changes preserve established
  grants? Resolve by a human-present positive upgrade and rollback experiment.
- **DQ2 Screen Recording:** Does the actual host-native capture operation retain
  host attribution and succeed for ungranted clients? Human-present experiment.
- **DQ3 Accessibility:** Does the actual host-native AX operation succeed and stay
  attributed to the host? Human-present experiment.
- **DQ4 Audio:** Which audio categories/session rules apply, and does each native
  operation succeed under the host identity? Human-present experiment.
- **DQ5 Notifications:** Does the host post with the intended sender/title and
  report denial accurately? Human-present experiment.
- **DQ6 Automation:** Does each allowlisted target use the host's target-specific
  consent, including new-target denial? Human-present experiment.
- **DQ7 Watchman integration:** Can the existing root-daemon topology/lifetime fit
  one consent-bearing host without root exec or another identity? Human-present
  experiment; no successful fit is claimed.
- **DQ8 Pinned restic worker:** Does a specifically pinned worker successfully
  perform FDA reads under the host, including changed worker bytes? Human-present
  positive experiment; denial attribution alone is insufficient.
- **DQ9 First Documents import:** Does bounded host-native copying reach one
  successful backup import with correlated audit/hash evidence? Human-present
  protected-read experiment plus consumer import receipt.
