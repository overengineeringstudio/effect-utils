# CI Tools Specification

This document specifies the CI tools deploy-preview and workflow-report control
plane. It builds on [requirements.md](./requirements.md).

## Status

Active

## Scope

This spec defines:

- the `@overeng/ci-tools` package and CLI identity
- deploy preview input, result, and failure modeling
- Netlify, Vercel, and Cloudflare Workers provider adapter boundaries
- workflow-report record emission for success, failure, and skipped deploys
- deploy task output emitted through `DEVENV_TASK_OUTPUT_FILE`
- OTEL span shape for deploy operations
- hermetic and live E2E test boundaries
- the remaining role of generated workflows and Nix tasks

Subsystems, each with its own requirements and spec:

- [01-quarantine/](./01-quarantine/spec.md) — what it means to hold a
  known-failing test target non-blocking, and how CI is told about one

This spec does not define:

- provider API protocols beyond the adapter operations used by this package
- provider project identifiers or secret values
- Storybook build behavior, except that Storybook output is a local artifact
  consumed by deploy previews
- quarantine entry semantics, expiry, or announcement channels
  ([01-quarantine/](./01-quarantine/spec.md))

## Architecture

```
GitHub Actions workflow (.github/workflows/ci.yml)
  │ generated by Genie
  │ calls devenv task or ci-tools directly
  ▼
devenv task modules
  │ stable task names: netlify:deploy:*, vercel:deploy:*
  │ pass static config + DEVENV_TASK_INPUT
  ▼
ci-tools Effect CLI
  ├─ workflow-report commands
  └─ deploy commands
       ├─ deploy core: schemas, errors, retry, telemetry, records
       ├─ Netlify provider adapter
       ├─ Vercel provider adapter
       └─ Cloudflare Workers provider adapter
             │
             ├─ provider APIs where stable
             └─ provider CLIs where upload/deploy semantics are safer to reuse
```

The Effect CLI is the source of truth for deploy semantics. Generated workflows
and Nix tasks are launchers that provide configuration and preserve existing
entrypoint names. Each reusable provider task module composes the shared
workflow-report tasks required by its generated deploy workflow; consumers do
not need a second import to make record collection and publication available.

Requirement trace: R01, R02, R03, R04, R24.

The package formerly named `@overeng/workflow-report` is
`@overeng/ci-tools`.

| Old identity               | New identity                                             |
| -------------------------- | -------------------------------------------------------- |
| `@overeng/workflow-report` | `@overeng/ci-tools`                                      |
| `workflow-report` binary   | `ci-tools` binary                                        |
| workflow-report CLI root   | `ci-tools workflow-report ...` or compatible subcommands |

## CLI Surface

The CLI exposes two groups.

```
ci-tools workflow-report collect-bundle ...
ci-tools workflow-report render-comment-body ...
ci-tools workflow-report find-comment ...

ci-tools deploy netlify ...
ci-tools deploy vercel ...
ci-tools deploy cloudflare-workers ...
```

Workflow-report commands preserve the current behavior: collecting marked
records, rendering managed comments, and locating managed comments.

Deploy commands accept explicit CLI options. Generated task wrappers parse
`DEVENV_TASK_INPUT` only to select deploy mode and PR number, then pass provider
configuration through typed CLI options. This keeps shell launchers thin while
making the Effect CLI the semantic boundary.

Human output follows the CLI design contract from R09-R11:

- failures emit a typed workflow-report failure record before exiting
- successes print one final URL line such as
  `Netlify deploy URL: https://example.netlify.app`
- every deploy outcome intended for PR reporting is emitted as a marked
  `WORKFLOW_REPORT_V1:` JSON line
- no decorative banners or repeated provider logs are added by `ci-tools`

Requirement trace: R09, R10, R11, R12.

## Deploy Domain Model

### Deploy Input

```ts
type DeployInputV1 = {
  readonly _tag: 'DeployInput'
  readonly schemaVersion: 1
  readonly provider: 'netlify' | 'vercel' | 'cloudflare-workers'
  readonly target: string
  readonly displayName?: string
  readonly mode: 'prod' | 'pr' | 'draft' | 'preview'
  readonly artifactDir: string
  readonly alias?: string
  readonly pr?: number
  readonly gitSha?: string
  readonly runId?: string
  readonly workflowReportOutputFile?: string
  readonly e2e?: {
    readonly enabled: boolean
    readonly allowSharedProject: boolean
    readonly reservedAliasPrefix: string
    readonly verifyContent?: {
      readonly path: string
      readonly expectedText: string
    }
  }
  readonly providerConfig:
    NetlifyProviderConfig | VercelProviderConfig | CloudflareWorkersProviderConfig
}
```

Provider config contains only non-secret identifiers and environment variable
names for secrets. Secret values are resolved at the process edge and redacted
from records, logs, and telemetry.

For Workers, `artifactDir` carries the consumer's `cwd`, not a static upload
directory. `CloudflareWorkersProviderConfig` is a tagged config containing
`config` (a non-empty Wrangler configuration path), `workerName` (the configured
Worker's exact name), `accountIdEnv`, and `authTokenEnv` (environment variable
names). The result's optional `deployId`
contains the uploaded/deployed Worker version UUID and is also exposed as
`DEPLOY_ID` in task output and `deployId` in report data when present.

### Deploy Result

```ts
type DeployResultV1 = {
  readonly _tag: 'DeployResult'
  readonly schemaVersion: 1
  readonly provider: 'netlify' | 'vercel' | 'cloudflare-workers'
  readonly target: string
  readonly mode: string
  readonly deployId?: string
  readonly rawDeployUrl: string
  readonly finalUrl: string
  readonly alias?: string
  readonly startedAtUtc: string
  readonly endedAtUtc: string
  readonly attempts: number
  readonly cleanup?: CleanupResult
}
```

### Deploy Errors

Expected failures are represented as `Schema.TaggedError` classes. The initial
tags are:

| Error tag                     | Retryable   | Meaning                                                                                                          |
| ----------------------------- | ----------- | ---------------------------------------------------------------------------------------------------------------- |
| `MissingAuth`                 | no          | Required provider token env var is absent or empty                                                               |
| `Unauthorized`                | no          | Provider rejected the token or account access                                                                    |
| `MissingBuildOutput`          | no          | Local artifact directory does not exist                                                                          |
| `ProviderProjectLookupFailed` | yes         | Provider project/site lookup failed or returned incomplete metadata                                              |
| `InvalidProviderOutput`       | no          | Provider CLI/API response does not decode to the expected schema                                                 |
| `ProviderOperationFailed`     | conditional | Provider command/API failed without a more specific classification                                               |
| `AliasAssignmentFailed`       | no          | Alias could not be assigned after collision handling; carries the classified inner failure and the attempt count |
| `UnsafeE2EAlias`              | no          | Live E2E attempted a shared-project alias outside the reserved namespace                                         |
| `VerificationFailed`          | yes         | Deployed URL did not serve the expected local fixture content                                                    |

Unexpected defects remain defects. They are not converted into expected domain
errors unless the boundary has enough information to classify them.

Netlify static deploys may emit a skipped record when an optional static output
directory is absent. A Netlify deploy may also opt into
`unauthorizedPolicy=skip`: both API lookup and CLI rejection then emit the same
structured skipped record. The default remains `fail`, and the shared workflow
composition never opts into this policy for PR previews or production deploys:
a present but rejected token is a configuration defect that fails the check.
Only absent credentials (`missingAuthPolicy=skip`, e.g. fork PRs) skip. Vercel
deploys treat missing configured artifact output as `MissingBuildOutput`
because the artifact path is the deploy input.

Requirement trace: R05, R06, R08.

## Provider Adapter Contract

```
DeployProvider
  resolveProject(input)       // API preferred
  diagnoseAuth(input)         // API preferred
  deployStaticDirectory(input)
  assignAlias(input, result)  // API preferred
  verify(input, result)
  cleanup(input, result)      // API preferred, best effort
```

Each provider adapter declares which operations use direct API and which use CLI
fallback. CLI fallback is acceptable for upload/deploy operations when it avoids
reimplementing provider-specific file upload semantics.

Provider API lookup and live verification HTTP calls use the Effect platform
`HttpClient` through the runtime `FetchHttpClient.layer`. Provider CLI fallback
is wrapped by Effect functions and classifies failures into deploy error tags.

Requirement trace: R07, R08, R13, R15.

## Netlify Provider

The Netlify adapter supports Storybook static directory deployment to one
configured site.

```
ci-tools deploy netlify
  ├─ resolve site by configured site id             // API preferred
  ├─ deploy local artifact directory                // CLI fallback allowed
  ├─ assign alias for prod/pr modes                 // API preferred when safe
  ├─ verify live E2E URL when requested             // HTTP GET
  └─ cleanup alias/deploy when provider supports it // best effort
```

The adapter classifies the known Netlify CLI failure
`Project not found. Please rerun "netlify link"` as
`ProviderProjectLookupFailed` unless direct API diagnostics prove a more
specific cause.

Unauthorized project access is classified identically at the API and CLI
boundaries. With the default `unauthorizedPolicy=fail`, it emits a failure
record and exits non-zero. With the explicit `skip` policy, it emits a skipped
record and exits zero. The policy never changes
the classification or retryability of the underlying provider response.

The Netlify task launcher passes `--workspace-filter` when a deployment opts
into workspace filtering and a package name can be derived from the artifact
directory's sibling `package.json`.

Requirement trace: R13, R14, R15, R17.

## Vercel Provider

The Vercel adapter supports local prebuilt or static artifact deployment to the
configured project/team boundary.

```
ci-tools deploy vercel
  ├─ resolve project/team configuration             // API preferred
  ├─ deploy local artifact directory or prebuilt out // CLI fallback allowed
  ├─ assign alias for prod/pr modes                 // API preferred when safe
  ├─ verify live E2E URL when requested             // HTTP GET
  └─ cleanup alias/deploy when provider supports it // best effort
```

The adapter must not trigger Vercel's provider-side build system. It deploys
local artifacts only.

For static artifacts, `ci-tools` creates a Vercel Build Output API work
directory with `.vercel/output/static`. For prebuilt artifacts, the task module
first runs `vercel pull` and `vercel build` locally, then passes the resulting
`.vercel/output` directory to `ci-tools deploy vercel --artifact-kind
prebuilt-output`. Team projects may pass `--scope-env` so the provider CLI is
scoped without committing account identifiers.

Prod and PR modes assign a deterministic `<aliasPrefix or target>.vercel.app`
host (PR mode appends `-pr-<number>`). When Vercel reports the host as already
in use, the adapter resolves the current holder: a deployment of the same
commit succeeds immediately, a same-project holder is rechecked exactly once,
and a holder outside the project fails fast with `AliasAssignmentFailed` whose
message names the remedy (`--alias-prefix` with a globally unique value, or an
explicit production domain). `*.vercel.app` hosts are a global namespace across
Vercel accounts, so a derived name claimed by another account can never be
assigned.

Requirement trace: R13, R14, R15, R16, R17.

## Cloudflare Workers Provider

```
consumer build -> Wrangler config + local output
  -> cloudflare-workers:deploy:<target> -> ci-tools deploy cloudflare-workers
       ├─ prod: Wrangler deploy with config-owned custom domains
       └─ pr: Wrangler version upload with stable and immutable preview URLs
  -> workflow-report record -> managed PR comment / job summary
```

The consumer owns the application build and its environment. `ci-tools` invokes
Wrangler deploy/version upload without orchestrating a separate application
build. Wrangler can still bundle code or execute configuration-defined build
commands; this is part of the executable-code trust boundary, not a sandbox.
Pass the already prepared Wrangler configuration and working directory:

```sh
ci-tools deploy cloudflare-workers \
  --target web \
  --worker-name web \
  --config dist/wrangler.json \
  --cwd apps/web \
  --mode prod \
  --production-domain app.example.com \
  --wrangler-bin wrangler

ci-tools deploy cloudflare-workers \
  --target web \
  --worker-name web \
  --config dist/wrangler.json \
  --cwd apps/web \
  --mode pr --pr 42 \
  --wrangler-bin wrangler
```

`--production-domain HOST` is repeatable and declares expected/report hostnames,
not desired state for a separate domain API. Production domain ownership lives
in the Wrangler configuration; Wrangler reconciles it during deploy, and
`ci-tools` verifies that Wrangler output contains the expected hosts. PR
versions do not take over production routes: the stable `preview_alias_url`
is the final URL and the immutable `preview_url` is the raw deployment URL.
Credentials are inherited from the invoking environment:
`--auth-token-env` defaults to
`CLOUDFLARE_API_TOKEN`, and `--account-id-env` defaults to
`CLOUDFLARE_ACCOUNT_ID`. These options name environment variables, never secret
values. Use an account-scoped token with only the Worker and domain/zone
permissions required by the configured deployment.

`--worker-name` is required and must match the consumer's Wrangler configuration.
Before invoking Wrangler, the adapter performs an authenticated
`GET /accounts/{account}/workers/scripts/{worker}/settings` lookup.
`--cloudflare-api-base-url` defaults to `https://api.cloudflare.com/client/v4`;
the override permits hermetic provider tests. HTTP 401/403 is `Unauthorized`;
404 and other lookup API failures are `ProviderProjectLookupFailed`, with
429/5xx and transport failures marked transient. Response bodies and credentials are not diagnostics.

The reusable `cloudflare-workers.nix` task module owns deployment configuration
(`name`, `workerName`, `config`, `cwd`, and `productionDomains`) and the consumer build
prerequisite through `afterTask`. It exposes `cloudflare-workers:deploy` and
`cloudflare-workers:deploy:<target>`, accepting `type=prod|pr` and `pr=N` for
PR mode. The aggregate and per-target tasks inherit the build environment.

### Executable-code trust boundary

Worker code, Wrangler configuration, build scripts, and configuration loading
are executable inputs, not safe static upload artifacts. Separating an
untrusted build from a credentialed Wrangler invocation does not make an
untrusted Worker deployment safe.

`genie/deploy-preview/cloudflare-workers.ts` exports
`cloudflareWorkersDeployJobs`, which guards the **entire job** before checkout,
build prerequisites, or credential-bearing environment variables are available.
Its non-overridable event predicate admits pushes to the main branch
(`mainBranch`, default `main`), `pull_request` events whose head repository equals
`github.repository`, and `repository_dispatch` events whose `github.event.action`
is in the explicitly declared `dispatchTypes` list and whose `github.ref` equals
the main branch ref. Fork PRs, `pull_request_target`, undeclared dispatch types,
and all other event types are excluded. `deployCondition` can restrict this
predicate but cannot widen it.
`cloudflareWorkersTrustedJobCondition` is the default string predicate (main
pushes and same-repository PRs, without dispatch admission).
`cloudflareWorkersTrustedJobConditionFor(options)` returns the predicate for
configured event options; its default output equals the string export.

`cloudflareWorkersDeployTriggers({ mainBranch, dispatchTypes })` supplies the
workflow `on` fragment for main pushes, PRs, and optional repository dispatches.
It emits `repository_dispatch: { types: [...] }` only for a non-empty list.
Dispatch types must be non-empty strings without wildcards; both the trigger
and job helpers validate them. Pass the same event options to both helpers.
Adding a trigger manually does not admit dispatches without declared types in
the job helper.

Repository dispatch requires a repository-write token, the same trust level as
a main push, and runs default-branch code. Dispatch runs use production deploy
mode, never PR mode. The helpers do not read `client_payload` in conditions,
environment variables, or commands. Dispatches and main pushes share a
per-target production concurrency group; PRs use separate per-PR groups.

The consumer supplies job-local credentials through `env`, setup steps through
`baseSteps`, and the existing `runDevenvTasksBefore` callback. Do not put
Cloudflare credentials in workflow-global environment variables. Same-repository
PR authors are explicitly trusted to execute code with these credentials; use
repository permissions and environment approval policies accordingly.
The low-level `cloudflareWorkersDeployStep` is only a launcher and does not
replace the job helper's trust boundary.

The helper's report job uses the existing collector, comment-body renderer,
and publisher, with managed state `cloudflare-workers-deploy-preview`.
It has the same event trust predicate, separate GitHub comment permissions,
and no Cloudflare job environment. Consumers provide trusted checkout/setup
steps via `commentBaseSteps` (defaulting to `baseSteps`). Deploy jobs upload
their JSONL reports with `actions/upload-artifact@v4`, including after deploy
failure. The comment job downloads and merges these artifacts before collection;
separate runners need not share report files. Production runs publish a summary;
trusted PR runs maintain the managed preview comment.

### Live E2E guardrails, marker verification, and cleanup

The opt-in live test remains skipped unless
`CI_TOOLS_CLOUDFLARE_WORKERS_LIVE=1`. It separately requires
`CI_TOOLS_CLOUDFLARE_WORKERS_ALLOW_SHARED_PROJECT=1`, a Worker name in
`CI_TOOLS_CLOUDFLARE_WORKERS_WORKER_NAME`, and an explicitly reserved namespace
in `CI_TOOLS_CLOUDFLARE_WORKERS_RESERVED_ALIAS_PREFIX` (for example,
`ci-tools-e2e`). Credentials come only from `CLOUDFLARE_API_TOKEN` and
`CLOUDFLARE_ACCOUNT_ID`; `CI_TOOLS_LIVE_WRANGLER_BIN` optionally selects Wrangler.
No live provider identifiers belong in the repository.

Shared-project E2E is PR/version-upload only, never production deployment.
`--e2e-allow-shared-project` requires `--e2e-reserved-alias-prefix`,
`--e2e-verify-path`, and `--e2e-verify-text`. The explicit `--preview-alias`
must start with that namespace before any upload; ordinary PR deployments
default to `pr-N`. The test chooses a unique reserved alias and writes a local
Worker module returning a unique marker, plus its Wrangler configuration.

After upload, the adapter uses Effect `HttpClient` to fetch the verification
path on the final preview alias URL and requires a successful HTTP response
containing that local artifact's marker. An HTTP or content failure is
`VerificationFailed`, not a successful upload-only test.

Once the upload record supplies an exact version UUID, cleanup owns every
subsequent output decode, URL validation, and marker-verification path,
including failures before a valid deploy result exists. It deletes only that UUID. The
[Cloudflare beta version-delete API](https://developers.cloudflare.com/api/resources/workers/subresources/beta/subresources/workers/subresources/versions/methods/delete/)
accepts a Worker ID or name at
`DELETE /accounts/{account}/workers/workers/{worker}/versions/{version}`.
Cleanup never deletes the Worker, changes production traffic, or uses `latest`
or an abbreviated UUID selector. A missing exact UUID records skipped cleanup.
HTTP/API/transport cleanup failures are best effort: successful verification
still returns its typed `CleanupResult`, and post-upload output or verification
failures retain their original classification with cleanup status in diagnostics. Cleanup failure
must not replace the original deploy or verification failure.

Requirement trace: R02, R06, R07, R08, R12, R15, R17, R18, R19, R20, R21, R22,
R23, R24.

## Retryability Policy

Retry is based on typed error tags, not raw exit codes.

| Error tag                     | Current policy                                         |
| ----------------------------- | ------------------------------------------------------ |
| `ProviderProjectLookupFailed` | recorded as retryable; Netlify API rate limits retried |
| `ProviderOperationFailed`     | retryable only when classified as transient            |
| `VerificationFailed`          | retry verification before failing the deploy           |
| all others                    | no retry                                               |

Attempt count is included in `DeployResultV1` and workflow-report records.

A Netlify site lookup answered with HTTP 429 is transient. The adapter retries
it at most three times. It never retries before the provider deadline:
`Retry-After` (seconds or HTTP date) takes precedence, then
`X-RateLimit-Reset` (Unix seconds). If neither header is present, it backs off
exponentially from one second. Scheduled waits are capped at 60 seconds in
total. When the provider's deadline lies beyond that cap, the adapter fails
immediately and does not retry early. No upload runs until the lookup succeeds.
The recorded attempt count includes every lookup request.

## Telemetry

The CLI uses the repo's existing Effect OTEL front door with service identity:

| Resource field      | Value                |
| ------------------- | -------------------- |
| `service.name`      | `ci-tools-cli`       |
| `service.namespace` | `overeng`            |

## E2E Strategy

### Required Hermetic E2E

Required CI runs hermetic fake-provider E2E through the same boundary used by
normal deploys:

```
devenv task -> ci-tools deploy -> fake provider -> workflow-report record
```

Required cases:

- success record is emitted
- known provider lookup failure is classified and marked retryable
- a rate-limited Netlify lookup waits for the provider deadline, retries, and
  bounds repeated rate limits
- unauthorized auth is classified and not retried
- unauthorized optional previews emit a skipped record only under the explicit
  skip policy
- invalid provider output fails as `InvalidProviderOutput`
- unsafe E2E alias is refused
- no secret-like value appears in logs or records

The task-boundary E2E also verifies `DEVENV_TASK_OUTPUT_FILE` URL metadata and
Vercel prebuilt-output delegation.

### Non-required Live E2E

Normal CI also runs non-required live Netlify and Vercel E2E jobs when secrets
are available.

Cloudflare Workers live E2E is opt-in and skipped by default. This integration
does not claim a live deployment was exercised. Set
`CI_TOOLS_CLOUDFLARE_WORKERS_LIVE=1` and provide
`CI_TOOLS_CLOUDFLARE_WORKERS_CONFIG` for an explicitly authorized,
disposable Worker configuration; the opt-in suite accepts
`CI_TOOLS_CLOUDFLARE_WORKERS_CWD` and `CI_TOOLS_LIVE_WRANGLER_BIN` overrides.
It uploads only a PR
version (`pr-999999`), never deploys production, and does not delete uploaded
versions. The consumer owns disposal of that Worker. Hermetic provider coverage
is the default boundary. The Netlify/Vercel shared-static-project E2E permission
does not authorize deploying executable Workers or mutating their domains.

Netlify/Vercel live E2E flow:

1. create a tiny local static directory containing run id, provider, target, and
   timestamp
2. call `ci-tools deploy <provider>` in E2E mode
3. require `--e2e-allow-shared-project`
4. require alias prefix `ci-tools-e2e-`
5. upload the local directory without provider build/CI
6. fetch the final URL and assert the marker text is present
7. attempt cleanup where provider APIs support it
8. emit a success or failure workflow-report record with cleanup status

Cleanup failures degrade the record but do not mask deploy or verification
failure.

The Vercel live test emits an allowlisted structured failure summary before
deleting its temporary directory. It parses the workflow report and publishes
only the child exit status, known deploy error tags and operation names, and
numeric API/HTTP status codes. Provider-operation failures include their typed
operation in the report. Unknown classifications, malformed reports, free-form
fields, and raw stdout/stderr are omitted, regardless of encoding. Missing
reports leave only the exit status. Successful assertions emit no summary.

Requirement trace: R18, R19, R20, R21, R22, R23.

## Generated Workflow and Nix Boundaries

Generated workflow steps call `ci-tools` and collect workflow-report records.
They do not construct deploy success/failure JSON themselves except for
minimal fallback when the CLI cannot be invoked.

Nix task modules keep existing task names:

```
netlify:deploy
netlify:deploy:<target>
vercel:deploy:<target>
cloudflare-workers:deploy
cloudflare-workers:deploy:<target>
```

Those tasks become thin launchers that serialize configured provider inputs and
call `ci-tools deploy`.

Requirement trace: R02, R17, R24.

## Open Design Questions

- **DQ1 Direct deploy APIs:** Which provider deploy/upload operations can move
  from CLI fallback to direct API without reimplementing fragile provider file
  upload semantics?
- **DQ2 Platform command execution:** Provider CLI fallback failures are typed
  and recorded today. Replacing the remaining Node command runner with
