# CI Tools Specification

This document specifies the CI tools deploy-preview and workflow-report control
plane. It builds on [requirements.md](./requirements.md).

## Status

Draft

## Scope

This spec defines:

- the `@overeng/ci-tools` package and CLI after the hard rename
- deploy preview input, result, and failure modeling
- Netlify and Vercel provider adapter boundaries
- workflow-report record emission for success, failure, and skipped deploys
- OTEL span shape for deploy operations
- hermetic and live E2E test boundaries
- the remaining role of generated workflows and Nix tasks

This spec does not define:

- the Netlify or Vercel provider API protocols beyond the adapter operations
  used by this package
- provider project identifiers or secret values
- Storybook build behavior, except that Storybook output is a local artifact
  consumed by deploy previews

## Architecture

```
GitHub Actions workflow (.github/workflows/ci.yml)
  │ generated by Genie
  │ calls devenv task or ci-tools directly
  ▼
devenv task modules
  │ stable task names: netlify:deploy:*, vercel:deploy:*
  │ pass static config + DEVENV_TASK_INPUT
  ▼
ci-tools Effect CLI
  ├─ workflow-report commands
  └─ deploy commands
       ├─ deploy core: schemas, errors, retry, telemetry, records
       ├─ Netlify provider adapter
       └─ Vercel provider adapter
             │
             ├─ provider APIs where stable
             └─ provider CLIs where upload/deploy semantics are safer to reuse
```

The Effect CLI is the source of truth for deploy semantics. Generated workflows
and Nix tasks are launchers that provide configuration and preserve existing
entrypoint names.

## Package and Binary Rename

The package currently named `@overeng/workflow-report` becomes
`@overeng/ci-tools`.

| Old identity               | New identity                                             |
| -------------------------- | -------------------------------------------------------- |
| `@overeng/workflow-report` | `@overeng/ci-tools`                                      |
| `workflow-report` binary   | `ci-tools` binary                                        |
| workflow-report CLI root   | `ci-tools workflow-report ...` or compatible subcommands |

The migration is a hard rename. Generated package manifests, TypeScript
references, Nix package builders, Genie imports, and generated CI workflow call
sites move to the new identity in the migration PR.

## CLI Surface

The CLI exposes two groups.

```
ci-tools workflow-report collect-bundle ...
ci-tools workflow-report render-comment-body ...
ci-tools workflow-report find-comment ...

ci-tools deploy netlify ...
ci-tools deploy vercel ...
```

Workflow-report commands preserve the current behavior: collecting marked
records, rendering managed comments, and locating managed comments.

Deploy commands accept either structured JSON input or explicit CLI options. The
generated task wrappers prefer structured JSON so config can be passed without
shell parsing logic.

## Deploy Domain Model

### Deploy Input

```ts
type DeployInputV1 = {
  readonly _tag: 'DeployInput'
  readonly schemaVersion: 1
  readonly provider: 'netlify' | 'vercel'
  readonly target: string
  readonly displayName?: string
  readonly mode: 'prod' | 'pr' | 'draft' | 'preview'
  readonly artifactDir: string
  readonly alias?: string
  readonly pr?: number
  readonly gitSha?: string
  readonly runId?: string
  readonly workflowReportOutputFile?: string
  readonly e2e?: {
    readonly enabled: boolean
    readonly allowSharedProject: boolean
    readonly reservedAliasPrefix: string
    readonly verifyContent?: {
      readonly path: string
      readonly expectedText: string
    }
  }
  readonly providerConfig: NetlifyProviderConfig | VercelProviderConfig
}
```

Provider config contains only non-secret identifiers and environment variable
names for secrets. Secret values are resolved at the process edge and redacted
from records, logs, and telemetry.

### Deploy Result

```ts
type DeployResultV1 = {
  readonly _tag: 'DeployResult'
  readonly schemaVersion: 1
  readonly provider: 'netlify' | 'vercel'
  readonly target: string
  readonly mode: string
  readonly deployId?: string
  readonly rawDeployUrl: string
  readonly finalUrl: string
  readonly alias?: string
  readonly startedAtUtc: string
  readonly endedAtUtc: string
  readonly attempts: number
  readonly cleanup?: CleanupResult
}
```

### Deploy Errors

Expected failures are represented as `Schema.TaggedError` classes. The initial
tags are:

| Error tag                     | Retryable   | Meaning                                                                  |
| ----------------------------- | ----------- | ------------------------------------------------------------------------ |
| `MissingAuth`                 | no          | Required provider token env var is absent or empty                       |
| `Unauthorized`                | no          | Provider rejected the token or account access                            |
| `MissingBuildOutput`          | no          | Local artifact directory does not exist                                  |
| `ProviderProjectLookupFailed` | yes         | Provider project/site lookup failed or returned incomplete metadata      |
| `InvalidProviderOutput`       | no          | Provider CLI/API response does not decode to the expected schema         |
| `ProviderOperationFailed`     | conditional | Provider command/API failed without a more specific classification       |
| `UnsafeE2EAlias`              | no          | Live E2E attempted a shared-project alias outside the reserved namespace |
| `VerificationFailed`          | yes         | Deployed URL did not serve the expected local fixture content            |

Unexpected defects remain defects. They are not converted into expected domain
errors unless the boundary has enough information to classify them.

## Provider Adapter Contract

```
DeployProvider
  resolveProject(input)       // API preferred
  diagnoseAuth(input)         // API preferred
  deployStaticDirectory(input)
  assignAlias(input, result)  // API preferred
  verify(input, result)
  cleanup(input, result)      // API preferred, best effort
```

Each provider adapter declares which operations use direct API and which use CLI
fallback. CLI fallback is acceptable for upload/deploy operations when it avoids
reimplementing provider-specific file upload semantics.

## Netlify Provider

The Netlify adapter supports Storybook static directory deployment to one
configured site.

```
ci-tools deploy netlify
  ├─ resolve site by configured site id             // API preferred
  ├─ deploy local artifact directory                // CLI fallback allowed
  ├─ assign alias for prod/pr modes                 // API preferred when safe
  ├─ verify live E2E URL when requested             // HTTP GET
  └─ cleanup alias/deploy when provider supports it // best effort
```

The adapter classifies the known Netlify CLI failure
`Project not found. Please rerun "netlify link"` as
`ProviderProjectLookupFailed` unless direct API diagnostics prove a more
specific cause.

## Vercel Provider

The Vercel adapter supports local prebuilt or static artifact deployment to the
configured project/team boundary.

```
ci-tools deploy vercel
  ├─ resolve project/team configuration             // API preferred
  ├─ deploy local artifact directory or prebuilt out // CLI fallback allowed
  ├─ assign alias for prod/pr modes                 // API preferred when safe
  ├─ verify live E2E URL when requested             // HTTP GET
  └─ cleanup alias/deploy when provider supports it // best effort
```

The adapter must not trigger Vercel's provider-side build system. It deploys
local artifacts only.

## Retry Policy

Retry is based on typed error tags, not raw exit codes.

| Error tag                     | Policy                                       |
| ----------------------------- | -------------------------------------------- |
| `ProviderProjectLookupFailed` | retry with bounded exponential backoff       |
| `ProviderOperationFailed`     | retry only when classified as transient      |
| `VerificationFailed`          | retry verification before failing the deploy |
| all others                    | no retry                                     |

Attempt count is included in `DeployResultV1`, failure records, and telemetry.

## Workflow Report Emission

Deploy commands emit exactly one final `WorkflowReportRecord` for each target.

### Success

```json
{
  "_tag": "WorkflowReportRecord",
  "schemaVersion": 1,
  "id": "deploy-netlify-effect-react",
  "kind": "deploy-preview",
  "subject": { "id": "effect-react", "label": "effect-react" },
  "status": "success",
  "title": "effect-react preview deployed",
  "summary": "Preview is ready",
  "createdAtUtc": "2026-06-29T00:00:00Z",
  "links": [{ "label": "Preview", "url": "https://example.netlify.app", "primary": true }],
  "data": {
    "provider": "netlify",
    "target": "effect-react",
    "mode": "pr",
    "attempts": 1
  }
}
```

### Failure

```json
{
  "_tag": "WorkflowReportRecord",
  "schemaVersion": 1,
  "id": "deploy-netlify-effect-react",
  "kind": "deploy-preview",
  "subject": { "id": "effect-react", "label": "effect-react" },
  "status": "failure",
  "title": "effect-react preview failed",
  "summary": "Netlify project lookup failed",
  "createdAtUtc": "2026-06-29T00:00:00Z",
  "data": {
    "provider": "netlify",
    "target": "effect-react",
    "mode": "pr",
    "errorKind": "ProviderProjectLookupFailed",
    "retryable": true,
    "attempts": 3,
    "diagnostics": {
      "auth": "ok",
      "projectLookup": "failed"
    }
  }
}
```

Records may include sanitized diagnostic outcomes. They must not include tokens,
raw secret values, or private account details.

## Telemetry

The CLI uses the repo's existing Effect OTEL front door with service identity:

| Resource field      | Value                |
| ------------------- | -------------------- |
| `service.name`      | `ci-tools-cli`       |
| `service.namespace` | `overeng`            |
| `service.version`   | resolved CLI version |

Deploy spans:

| Span                       | Label              | Attributes                                          |
| -------------------------- | ------------------ | --------------------------------------------------- |
| `ci-tools.deploy`          | target             | provider, target, mode, run id                      |
| `ci-tools.deploy.provider` | provider           | provider, target                                    |
| `ci-tools.deploy.attempt`  | attempt number     | provider, target, mode, attempt, status, error kind |
| `ci-tools.deploy.verify`   | final URL host     | provider, target, status                            |
| `ci-tools.deploy.cleanup`  | alias or deploy id | provider, target, cleanup status                    |

Attributes must follow `@overeng/otel-contract` conventions. Secret values and
unbounded raw stderr are not span attributes.

## E2E Strategy

### Required Hermetic E2E

Required CI runs hermetic fake-provider E2E through the same boundary used by
normal deploys:

```
devenv task -> ci-tools deploy -> fake provider -> workflow-report record
```

Required cases:

- success record is emitted
- known provider lookup failure is classified and retried
- unauthorized auth is classified and not retried
- invalid provider output fails as `InvalidProviderOutput`
- unsafe E2E alias is refused
- no secret-like value appears in logs or records

### Non-required Live E2E

Normal CI also runs non-required live Netlify and Vercel E2E jobs when secrets
are available.

Live E2E flow:

1. create a tiny local static directory containing run id, provider, target, and
   timestamp
2. call `ci-tools deploy <provider>` in E2E mode
3. require `--e2e-allow-shared-project`
4. require alias prefix `ci-tools-e2e-`
5. upload the local directory without provider build/CI
6. fetch the final URL and assert the marker text is present
7. attempt cleanup where provider APIs support it
8. emit a success or failure workflow-report record with cleanup status

Cleanup failures degrade the record but do not mask deploy or verification
failure.

## Generated Workflow and Nix Boundaries

Generated workflow steps call `ci-tools` and collect workflow-report records.
They do not construct deploy success/failure JSON themselves except for
minimal fallback when the CLI cannot be invoked.

Nix task modules keep existing task names:

```
netlify:deploy
netlify:deploy:<target>
vercel:deploy:<target>
```

Those tasks become thin launchers that serialize configured provider inputs and
call `ci-tools deploy`.

## Open Design Questions

- **DQ1 Direct deploy APIs:** Which provider deploy/upload operations can move
  from CLI fallback to direct API without reimplementing fragile provider file
  upload semantics?
- **DQ2 Hard rename fallout:** Whether any downstream consumer depends on the
  old `workflow-report` binary name outside generated CI. The hard rename assumes
  repository-owned call sites can be updated atomically.
- **DQ3 Live E2E requiredness:** Live provider E2E is non-required initially.
  Making it required would require evidence that provider-side flake rate is
  low enough not to block unrelated PRs.
