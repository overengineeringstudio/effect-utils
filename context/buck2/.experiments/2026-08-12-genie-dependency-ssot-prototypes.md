# Genie Dependency SSOT Prototypes

Status: completed; decision evidence with production admission still pending

## Question

Can exact operation-local dependency roots reuse and recompose the existing
`package.json.genie.ts` source-of-truth chain without repeating dependency
declarations, versions, or resolver data?

## Candidates

| Candidate                                               | Result                      | Main finding                                                                                                                |
| ------------------------------------------------------- | --------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Typed dependency facet on the existing Genie output     | Selected, prototype partial | Runtime parity and locality pass; current composition types widen aliases and require a focused API correction              |
| Typed extraction from `GenieOutput.data`                | Pass with limitations       | Byte-compatible and useful for migration, but widened string keys lose compile-time alias safety and composition provenance |
| Dependency declarations name their consuming operations | Correct but rejected        | Avoids operation lists, but creates reverse consumer knowledge, rename fanout, and cyclic composition pressure              |

## Typed Export Prototype

`package.json.genie.ts` exported one typed semantic value and defaulted its
package JSON projection. BUCK and tsconfig projections imported the typed value
directly rather than parsing generated bytes.

The disposable prototype used 54 nonblank, noncomment authored lines across a
catalog, two package definitions, and two projection consumers. Each consumer
was three lines. It repeated no dependency map and no version literal. These
results establish design feasibility, not production admission: the fixture
and command were not retained in the repository.

| Oracle                                      | Result |
| ------------------------------------------- | ------ |
| Strict TypeScript checking                  | Pass   |
| Direct typed reuse                          | Pass   |
| No generated-output parsing                 | Pass   |
| Undeclared-root rejection                   | Pass   |
| Irrelevant-facet byte stability             | Pass   |
| Operation edit changes only Buck projection | Pass   |
| Package-local isolation                     | Pass   |

A second prototype against the real repository found two existing type
widenings. `packageJson` erases literal workspace package names, and omitted
`catalog.compose` buckets infer their broad constraints instead of empty
inputs. Consequently `keyof` the emitted dependency maps can widen to `string`.
The runtime and byte-parity controls passed, but compile-time rejection of an
unknown alias failed. Production must preserve a separately typed dependency
request facet during composition rather than reconstructing handles from the
current maps.

The repository also has rootable-field alias collisions in 9 of 36 generated
package manifests, with as many as 10 in one package. Handles are therefore
field-qualified, for example `dependencies.effect` and
`devDependencies.vitest`; a flat alias map is not exact.

## Output Extraction Prototype

Extracting dependency fields from the existing structured Genie output
preserved checked-in package JSON bytes through the normal formatter and
preserved a 1,604-byte BUCK projection exactly. Check and test operations each
selected two roots; an irrelevant package-only edit changed package JSON but
left BUCK bytes and roots unchanged.

Direct output inspection is not the long-term API because dependency keys widen
to `Record<string, string>` and the output no longer retains workspace/external
composition provenance. A supported typed facet on the same Genie value avoids
both defects.

## Dependency-Use Direction Prototype

The bounded oracle covered six operations across pnpm and Cargo, including two
same-role tests with different roots, eight declarations, and sixteen request
or alias mutations.

| Model                                       | Exact roots        | Same-role difference | Rename locality                            |
| ------------------------------------------- | ------------------ | -------------------- | ------------------------------------------ |
| Operation references typed handles          | Pass               | Pass                 | One declaration edit                       |
| Role-only applicability                     | Fail: over-selects | Fail                 | One declaration edit                       |
| Dependencies reference consuming operations | Pass               | Pass                 | Operation plus dependent declaration edits |

The operation-to-handle projection was byte-identical across equivalent
ordering and repeated runs. Its canonical output digest was
`29514acf015ccdbce0812417932fa76ec1e5cbd5f365c12eb98e556a5a305453`.

## Lifecycle and Type-Scale Prototypes

The following disposable lifecycle and scale probes were not retained as
reproducible admission fixtures. Genie may evaluate imported generator modules
more than once. Existing-file and generic-facet seams both evaluated semantic
initialization twice in all 24
discovery-entry order permutations. Pure, sorted values produced deterministic
bytes in every order. A bounded import-graph oracle exercised 128 likely edge
sets: the strict one-way graph was acyclic and all 127 reverse-edge variants
cycled; a real reverse import produced a temporal-dead-zone failure.

The existing non-emitted `GenieOutput.meta` channel is therefore the preferred
facet carrier. Values must be immutable structural data with stable logical
IDs, not symbols, object identity, mutable registries, counters, or import-time
registration. A separate non-`.genie.ts` model file is not selected because the
current watcher does not track transitive dependencies and compiled Genie does
not give it singleton semantics.

Branded handles were checked with TypeScript 5.9.3 at 30 modeled packages and
10 operations per package. At 100 dependencies per package, checking used 98
MB and 0.27 seconds. At 500 dependencies it used 211 MB and 0.89 seconds.
Leaking generic handle unions into normalized return types was a failure mode:
it emitted 37.9 MB of declarations and used 1.54 GB. Erasing generics at
operation normalization reduced the declaration to 11 KB.

## Conclusion

Extend the existing Genie package composition with a typed dependency facet in
`GenieOutput.meta`. `package.json.genie.ts` remains the package entry point and
default projection; it does not absorb operation definitions. Composition
creates field-qualified branded handles before its emitted maps widen.
Operations in `BUCK.genie.ts` reference those handles, authoring only the
irreducible use edge and no dependency data.

The import direction is one way: dependency-light helpers, then package
composition, then package JSON, BUCK, and tsconfig projections. Handles carry
only package scope, manifest field, alias, external/workspace provenance, and
logical first-party identity. They carry no selected version, resolver context,
physical path, or private workspace topology. Normalization resolves structural
references against canonical declarations, sorts and deduplicates roots, and
erases generic handle types. Peer declarations do not produce execution roots
until peer-context semantics are designed.

Parsing rendered package JSON is forbidden. Inspecting widened output data is a
migration adapter only. Role-wide defaults may be authoring sugar only when
they normalize into explicit operation-to-handle edges before semantic
identity. Production admission still requires retained RED/GREEN fixtures for
type rejection, byte parity, import cycles, privacy, foreign references, and
relevant and irrelevant invalidation.
