notion schema apply — provision your Notion database from a file

The honest inverse of codegen (3.1). Instead of generating code from Notion, declare the database you want in a typed file and have the tool reconcile Notion to match — additive and safe. This is a designed preview of where notion schema is headed, not a shipped feature.

Shipped codegen (3.1) goes one way: Notion → code. The reverse — a file that defines the database and provisions it — doesn't exist. So the schema itself is still authored by clicking around Notion's UI, with no diff, no review, no source of truth in git. This page previews the planned answer.

Like terraform plan: the planned notion schema plan would read the file, look at Notion, and print every change — + to add, ~ to change — creating nothing. Each line maps one-to-one to an operation the sync engine already supports. The planner that produces this output is the part that isn't built yet.

The first apply would create the database and write a tasks.notiondb.lock.json — the state file that records which Notion DB this file owns. A second run diffs the file against the live schema and reconciles only the delta (one option, one property); re-running an unchanged file is a no-op. The lock/state model is the least-settled part of the design — proposed here, not decided.

04…and destructive fails closedplanned front-end · real engine

It would only ever add. Anything that could lose data is refused.

✓ in scope · additive
+create database if absent
+add property (the conservative type subset only)
~rename property (needs an explicit renamedFrom hint)
~add select options (append-only)
✗ out of scope · fails closed
xremove a propertyBLOCKED · DestructiveSchemaMigrationRequired

✓ real today · the engine

The sync layer already adds properties, renames them, extends select options, and refuses destructive changes against a live Notion DB. Those guard names are the actual ones in notion-datasource-sync.

◷ planned · the front-end

What's not built: the declarative plan/apply commands, the planner that diffs a file against Notion, and the lock.json state model. A front-end doesn't get to weaken the guards.

This is why the direction is even worth considering: the boundary is inherited from an engine that already fails closed today. Deletes, type changes and option removals are done deliberately in Notion — never as a silent side effect of editing a file. And to be clear once more: this front-end is planned work; the engine exists, the commands don't.

Planned / roadmap preview — notion schema apply and notion schema plan do not ship today. The shipped inverse is 3.1 codegen (notion schema generate · DB → code). This page is the honest code → DB direction we'd build on top of the same engine.
