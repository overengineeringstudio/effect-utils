Notion tooling · overview

The Notion dev platform — and the four gaps it leaves open

Notion ships a capable developer platform. But between "raw API" and "how you actually want to work," four gaps recur. Here's the platform, and the tool that fills each gap.

The platform Notion gives you

API

REST over pages, blocks, and data sources. Typed property objects in, JSON out. The raw substrate everything else builds on.

CLI

ntn — scriptable access to the same API: query data sources, read and create pages as Markdown, upload files.

Workers

Server-side automation hosted in the workspace — event-driven jobs that react to changes without your own infra.

Powerful primitives — but each one leaves a workflow gap once you want typed, local, diffable, or declarative access.

The four gaps & the tool that fills each

01 notion md

GapNo first-class way to keep local Markdown in sync with pages — either side can silently clobber the other.

FixAn .nmd source of truth with a 3-way merge; divergence writes a conflict draft instead of overwriting.

02 notion db

GapNo way to edit a database as tabular, scriptable data — no SQL, no diffable file.

FixA local <db-id>.sqlite replica you edit with plain SQL; a guarded sync fails closed on unsafe writes.

03 notion schema

GapThe API hands you untyped JSON; a rename in Notion breaks you at runtime with no warning.

FixIntrospect into typed Effect schemas; a diff --exit-code CI gate fails the build on drift.

04 notion-react

GapThe block API is raw imperative append/update/delete — re-rendering means churn or a hand-rolled diff.

FixWrite pages as JSX; a reconciler diffs by blockKey and emits the minimum block ops.

The through-line: each tool is a stopgap for a first-class capability Notion doesn't yet ship — local sync, tabular editing, typed drift-checked schemas, and a declarative page API. Together they make Notion feel like a real, versionable developer substrate.
