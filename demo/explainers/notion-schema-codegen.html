The whole flow, in four steps

  1. 1Point at a live Notion database.
  2. 2Typed Effect schemas — generated, not written.
  3. 3Real autocomplete, real compile errors.
  4. 4A CI drift gate: the schema can't change without your build failing.

notion schema generate introspects the live database and writes a typed schema.gen.ts — every select becomes a literal union, so your editor autocompletes options and tsc rejects wrong ones. Change the database in Notion and notion schema diff --exit-code fails your build (exit 1). The arrow only runs Notion → code: it reads the database, never writes it.

Commit the generated schema and it's just code — versioned, reviewed in PRs, type-checked end to end. queryAll · get · create · update are all typed against the real database, so a wrong property name or option fails at compile time, not in production. List every DB you track in notion.config.ts and notion schema generate-config regenerates them all at once.

Be honest about what this is: introspect → codegen → drift detection. It reads Notion; it never writes it. You still create and change the database in Notion. notion schema diff <id> --file schema.gen.ts --exit-code mirrors the live DB against your committed types and fails CI (exit 1) the moment they disagree — so drift can't silently ship. Provisioning Notion from a file is the separate, planned inverse.

This is the DB → code direction: Notion owns the shape, your types follow. The honest inverse — declare the database in a file and provision Notion to match (code → DB) — is a separate, planned capability: see notion schema apply (3.2, roadmap).
